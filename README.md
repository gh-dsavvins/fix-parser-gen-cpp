# fix-parser-gen-cpp

A zero-allocation FIX protocol parser for C++, generated from a QuickFIX XML dictionary (FIX 4.4). C++ port of [fix-parser-gen](https://github.com/gh-dsavvins/fix-parser-gen).

The generator (`generator/generate.py`) turns the dictionary into typed C++ classes for every field, group and message. Messages are mapped rather than parsed: each field stores the offsets of its value in the raw bytes and decodes it only when read. Message objects are reused, so parsing allocates nothing.

Field separators (SOH) are found in one pass over the message, 16 bytes at a time with ARM NEON or SSE2 (scalar fallback on other CPUs); each field takes its end from that index instead of scanning.

Tags are matched without a branch per tag: the first 8 bytes of a field are loaded into one register, the `=` is found and the tag digits are converted with SWAR arithmetic, and one load from a generated per-message table (tag → field) picks the field. Undefined tags select the next entry of an unknown-field pool instead, and keep their position in the message.

Input is assumed to be well-formed FIX; the parser does not validate tags or framing.

## Test messages

`resources/synthetic_messages.txt`: 5,000 messages, 1.38 MB, generated by `generator/synth.py`. They are built so that the CPU's branch predictor cannot memorize them.

**Why not a small set of real messages.** A latency test loops over its messages millions of times. If the set is small, the branch predictor learns the whole sequence of decisions, and the test measures the CPU's memory of the benchmark instead of the parser. This was measured, not assumed: with a set of 42 real messages, an earlier version of this parser (a nested `switch` over the tag digits) mispredicted 1.7 branches per message on an Apple M2 Ultra. On unpredictable messages the same code mispredicted 54 per message, at about 25 cycles each, and ran 3.4 times slower. Its benchmark number was its best case, which live traffic does not give.

**How they are built.** Each message starts from one of 42 real FIX messages (ExecutionReport, NewOrderSingle, OrderCancelRequest, OrderCancelReplaceRequest, Reject), so the message mix and structure are real. Then:

- the header fields are shuffled (BeginString, BodyLength and MsgType stay first),
- each body field is dropped with probability 25%,
- up to 8 fields that the dictionary defines for that message type are added,
- every value is regenerated with a random length that fits its type (prices, quantities, 17- or 21-character timestamps, enum values, 1–20 character strings),
- the body fields are shuffled; a repeating group moves as one block,
- BodyLength and CheckSum are recomputed.

The result: 4,999 of the 5,000 messages have a distinct tag sequence. 4.15% of the fields are undefined for their message type in FIX 4.4 (tags 20, 47, 76 and 41, which come from the FIX 4.2 templates), so the unknown-field path is exercised too. The values are random, so the messages are valid FIX in structure but not consistent as orders; the parser does not look at that. Real traffic is more predictable than this, since a counterparty's engine writes fields in a fixed order, so this set is the hard case.

**Why 5,000.** The set only has to be longer than the predictor can remember. Measured on the current parser by taking the first N messages of a 100,000-message set (Apple M2 Ultra, clocks per byte assume 3.49 GHz):

| Messages | Size | Clocks per byte | Time per message |
|---|---|---|---|
| 42 | 12 KB | 1.49 | 120 ns |
| 300 | 84 KB | 1.57 | 126 ns |
| 1,000 | 276 KB | 2.29 | 184 ns |
| 3,000 | 816 KB | 2.68 | 212 ns |
| 5,000 | 1.38 MB | 2.72 | 215 ns |
| 10,000 | 2.7 MB | 2.76 | 218 ns |
| 100,000 | 27 MB | 2.81 | 222 ns |

Up to about 300 messages the predictor still learns the sequence. Between 300 and 3,000 the sequence outgrows it. 5,000 messages give 97% of the effect of 100,000 in 5% of the size. Memory is not a factor at any of these sizes: reading the messages costs under 0.2 clocks per byte, because they are read in order and the hardware prefetcher keeps up.

The 42 templates are not part of this repo; `synth.py` documents how the file was made (count 5000, seed 1).

## Build

Requires CMake 3.20+, a C++20 compiler and Python 3. CMake runs the generator when `generator/generate.py` or `resources/quickfix.44.xml` changes; generated sources go to `gen/`.

```
cmake -S . -B cmake-build-release -DCMAKE_BUILD_TYPE=Release
cmake --build cmake-build-release
cd cmake-build-release && ctest
./latency_test
```

Options: `FIX_NATIVE` (default ON, `-march=native` / `-mcpu=native`), `FIX_LTO` (default ON), `FIX_PGO` (`OFF`, `GENERATE`, `USE`).

## Tests

`field_by_field_test`: parses each of the 5,000 messages and checks every field, in order, against the raw message (tag and value, including unknown fields). All pass.

`latency_test [ghz=<clock>]`: 10,000,000 messages, cycling through the 5,000, single thread. Clocks per byte are computed from the given clock (default 3.49 GHz).

`breakdown_test`: splits the time into reading the message from memory and parsing it. Run as root, it also reads the CPU's hardware counters (cycles, instructions, branches, branch mispredictions; kperf on macOS, `perf_event_open` on Linux) and takes clocks per byte from measured cycles.

## Results

Apple M2 Ultra, Apple clang 21, `-O3`, native, LTO, single thread, clocks per byte assume 3.49 GHz:

```
avg message size:          275.30 bytes
time per byte               0.78 nanos
clock per byte              2.72
time per message          214.56 nanos
```

**2.72 clocks per byte, 215 ns per message** on the synthetic set. The earlier tag `switch` took 6.7 clocks per byte on unpredictable messages; the table removes about 300 branches per message and most of the mispredictions (54 → 12 per message).
